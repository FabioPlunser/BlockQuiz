\section{Design decisions}
\label{sec:design-decisions}
This chapter expalins the principal architectural choices behind BlockQuiz. The focus is on decisions that strongly influence the prototype: the visual editor technology, the execution model, the 
persistence layer and the seperation of concersn between exercise defintion, execution, grading and presetnation.

Blockly was selected because it offerse the best balance between maturtiy and adaptablity. 
Its toolbox model directly supports the pedagogical goal of restricting the available blocks on a per-exercise basis, which helps reduce unnecessary complexity 
for novice learners. The same integration can also be reused in both the learner-facing player and the teacher-facing CMS> 
A custom implementation would have provided greate control, but the additional development effort would have been difficutl to justify within the scope of the thesis. 
Scratch Blocks, while visually familiar, would have constrained the platform more strongly to an ecosystem that is not primrarly designed for this kind of custom guided-learing workflow. 

\subsection{Excecution mode: Client-Side sandbox}
The execution model is intentionally optimized for classroom repsonsiveness and low deployment complexity. 
A client-side iframe sandbox therefore represents a pragramtic compromise. It allows learners to receive immediat feedback without requiring the server to execute every submission, 
which keeps the overall system ligher and easier to deploy. 
At the same time, this decision does not remove all security concerns. 
The thesis therefore treats client-side execution as a risk-managed prototype choice rather than as a perfect isolation boundary. 
Since authenitcated submissions can additionally be re-executed on the server before they are stroed, the design combines responsive local interaction with a more trustworthy persistence path.

\section{Architectural Overview}
\label{sec:design-overview}
The sytstem follow a layered architecture in which the user interface, exercise logic, grading and persistence remain conceptually separate. This separation is visible in the code base: 
Svelte components are primarily responsible for presentation, wherease execution, graing, typing and persistence are handled in dedicated modules. 
The result is not only easier to reason about technically, but also easier to explain as part of the thesis.

\subsubsection{Frontend Layer}
The fronted is implemented with SvelteKit and primarily supports two interaction contexts. 
The learner interface presents an exercise together with Blockly workspace, a visual or textual output area and the resulting feedback. 
The teacher interface supports exercise authoring, review and course composition. 
The current implementation also contains additional management views, such as log inspection and user administration, but these play a secondary role in the argument of the thesis. 
The central design focus remainse the learner workflow and the teacher-facing authoring process. 


\subsubsection{Exercise Engines}
The exercise layer models the behavior of each supported task type, The Input/Output engine provides controlled input consumption and output collection for text-oriented tasks, while the turlte 
engine manges position, orientation, pen state and drawing history for visual exercises. 
Each exercise type is associated with an exercise definition, a Blockly toolbox and generator mapping, a restricted execution API and a grading strategy that matches the exercise semantics. 


\subsubsection{Sandbox}
The sandbox executes generated code in a restricted context. 
in practical terms, execution takes place in an iframe with restricitve sandbox setttings and all communication with the main application occurs to browser capabilities; 
they can only call the exercise-specific commands exposed by the application. 
Runtime guards additionally limit execution time and help detect non-terminating behavior. 
The resulting design does not claim absolute security, but it does establish a clear and trsut boundary that is appropriate for the protoype. 


\subsubsection{Graders}
The grading layer evaluates exercise outcomse after execution. 
For Input/Otuput tasks, this means comparing actual and expexted output across defined test cases. 
For tturlte exercsies, it measn comapring either the xecuted command trace or the resulting final state. 
Keepking grading separate from execution and presentation makes the platfrom easier to extend and allows the grading logic to be discussed indepentendtly of the user interface. 



\subsection{Data Model}
The data model stays close to the implemetned scope of the protoype. Its most important entities are users, exercsies, course, relations between courses and exercises, and attempt or progress revords. 
users store account and role information wherever authenticated access is needed. Exercsies contain the task definition and grading configuration. 
Coruses ogranize exercsies into ordered learning sequences, and the course-exercises relations capture both ordering and reuse. 
Attemtps or prgoress recorsd connect learners to exercises and presever the outcomse of their interaction with the platform. 
The repository also contains supporting entities such as audit logs, version tables and translations. 
Tehse are part of the braoder application context, but within the scope of the thesis they remain secondary to the core educational entities of exercises, courses, users and attempts. 

\subsection{Security Considerations}
The main threats considered in the design are accidental or malicious infinite loops, uinteded access to browser capabilities from learner code, and unauthorized access to protected authoring features. 
The response to these threats is deliberatley layered. Iframe-bases andboxing limits the execution context, command whitelisting constrains the API available to generated programs and timeout or step-based execution limits keep 
programs fro running indefinetly. 
In paralle, validation of application input and API payloads protects the wider application, while role-based authorization seperates leraner, authoring and management privileges. 
These measures reduce risk for the intended educational prototype but they do not justify absolute security claims.
