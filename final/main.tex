% Slide 2 — Motivation
% SAY: - Computational thinking is now a school topic, not a niche skill.
%      - Austria made "Digitale Grundbildung" mandatory in 2022/23.
%      - The existing tools are good, but none fits the specific classroom
%        need. Point at each with the laser, one line each.
%      - Then read out "the gap" slowly; that is what the thesis targets.
% ============================================================
\begin{frame}{Motivation \& the gap}
  Digitale Grundbildung is mandatory in Austrian schools since 2022/23,
  but the available block tools do not fit classroom constraints \cite{digitaleGrunbildung}.
  \begin{itemize}
    \item \textbf{Scratch} -- creative, open-ended, no deterministic grading
    \item \textbf{Code.org} -- well scaffolded, but cloud-only
    \item \textbf{MakeCode} -- great for hardware, less for assessment
    \item \textbf{Blockly} -- a library, not a platform on its own
  \end{itemize}
  The gap: short, gradable exercises a teacher can author, with a
  privacy-conscious deployment that fits a school network.
\end{frame}

% ============================================================
% Slide — Requirements
% SAY: - These come from the target group and the classroom context.
%      - Stress the three that drive the design: easy authoring, immediate
%        feedback, automatic grading. The rest support those.
% ============================================================
\begin{frame}{Requirements}
  \begin{itemize}
    \item Teachers author exercises and courses without coding
    \item Learners get immediate, understandable feedback
    \item Automatic grading, plus a hint system for support
    \item Multiple exercise types
    \item Bilingual (DE/EN) UI and content
    \item Safe execution of learner code
  \end{itemize}
\end{frame}

% ============================================================
% Slide 3 — BlockQuiz overview
% SAY: - The whole system on one slide. Name the three types and the stack,
%        then go straight into the demo so they see it instead of reading.
% ============================================================
\begin{frame}{BlockQuiz in one slide}
  A web platform for short block-programming exercises:
  \begin{itemize}
    \item Three exercise types: \texttt{io}, \texttt{turtle}, \texttt{robot}
    \item Per-exercise constrained Blockly toolbox
    \item Browser sandbox + authoritative server-side regrading
    \item Teacher CMS, class system with IdP sync, cohort analytics
    \item Self-hosted, SQLite, no required external services
  \end{itemize}
  {\footnotesize Built with SvelteKit, Svelte~5, Blockly, Bun, Drizzle ORM, Better Auth.}
\end{frame}

% ============================================================
% Slide — Dual-path execution (the strongest technical claim)
% SAY: - This is the key technical idea: every submission runs twice.
%      - Left: the browser sandbox gives the learner instant feedback.
%      - Right: the server re-runs the SAME code in an isolated subprocess,
%        no DB, no session, and THAT score is the one we store.
%      - So: speed for the learner, trust for the database.
% ============================================================
\begin{frame}{How it works: dual-path execution}
  Every submission is executed twice, by design.
  \begin{columns}[T]
    \begin{column}{0.48\textwidth}
      \textbf{Browser path (immediate)}
      \begin{itemize}
        \item Hidden iframe, blocked globals
        \item Time / step / loop limits
        \item learner sees feedback now
      \end{itemize}
    \end{column}
    \begin{column}{0.48\textwidth}
      \textbf{Server path (authoritative)}
      \begin{itemize}
        \item Isolated Bun subprocess, \texttt{node:vm}
        \item No DB, no session, hard kill timeout
        \item the stored score, not the client's
      \end{itemize}
    \end{column}
  \end{columns}
\end{frame}

% ============================================================
% Slide — Grading & publish validation
% SAY: - All three types return the same result shape, so the UI and analytics
%        do not care which type it is.
%      - Visual tasks grade the command trace, not pixels, so grading is
%        deterministic and testable.
%      - The publish gate stops broken exercises from reaching learners.
% ============================================================
\begin{frame}{Grading \& publish validation}
  One result shape for all types: pass/fail, score, per-test feedback.
  \begin{itemize}
    \item \texttt{io}: normalised string compare (trim, whitespace, case)
    \item Visual: command-trace replay, not pixels, deterministic
  \end{itemize}
  \vspace{0.3cm}
  \textbf{Publish gate} blocks broken exercises: bilingual content, parseable
  starter XML, block ids in toolbox, $\ge 1$ test, and BFS reachability for
  turtle/robot.
\end{frame}

% Slide — Class system & IdP sync
% SAY: - Cohorts are first-class and can sync to the school identity provider.

%      - On every login the IdP rows are reconciled; manual rows are never

\begin{frame}{Class system \& identity-provider sync}
  Cohorts are first-class and can sync to the school IdP.
  \begin{itemize}
    \item Two membership sources per row: \emph{manual} (admin) and \emph{sso} (IdP)
    \item On every SSO login, IdP rows are reconciled, manual rows untouched
    \item Course assignment by class
  \end{itemize}
  Roster stays in sync with the school IdP without a separate SCIM endpoint.
\end{frame}

% Slide — Pedagogical design rationale
% ============================================================
% SAY: - The design is not arbitrary; each choice maps to a learning theory.
%      - Constrained toolbox -> Cognitive Load Theory.
%      - Staged hints -> Zone of Proximal Development / scaffolding.
%      - Replay + plain-language readout -> debugging as a CT skill.
%      - And each one is captured per attempt, so it becomes an analytics
%        signal, not just a feature.
\begin{frame}{Pedagogical design rationale}
  Each design choice is anchored in learning theory:
  \begin{itemize}
    \item Per-exercise toolbox $\rightarrow$ Cognitive Load Theory \cite{sweller1988}
    \item Staged, captured hints $\rightarrow$ Zone of Proximal Development \cite{Vygotsky1980}
    \item Replay + plain-language readout $\rightarrow$ debugging as a computational thinking skill
          \cite{brennan2012}, blocks-to-text bridge \cite{weintrop2015}
  \end{itemize}
  Each one is captured per attempt and surfaced in analytics.
\end{frame}

% ============================================================
% Slide — Lessons learned
% SAY: - The typed exercise model was the best decision; it kept everything
%        consistent as the system grew.
%      - The message-based sandbox made the subprocess regrading a small add-on.
%      - The publish gate caught real mistakes during my own development.
%      - Betting on the experimental SvelteKit features paid off.
% ============================================================
\begin{frame}{Lessons learned}
  \begin{itemize}
    \item Typed discriminated-union exercise model: keeps CMS, player, sandbox,
          analytics honest as the system grew
    \item Message-based sandbox protocol, made subprocess regrading a small addition, not a refactor
    \item Publish-validation gate, caught real authoring mistakes during development
    \item Using SvelteKit experimental features, remote functions and async svelte
  \end{itemize}
\end{frame}

% ============================================================
% Slide — Limitations & future work

\begin{frame}{Limitations \& future work}
  \textbf{Limitations of this thesis}
  \begin{itemize}
    \item User study: $n = 2$, student teachers only, no child participants
    \item Exercise type addition requires quite extensive code changes, but has been simplified as much as possible
  \end{itemize}
  \vspace{0.2cm}
  \textbf{Future work}
  \begin{itemize}
    \item Classroom pilot with children in the 8-12 target range
    \item Blocks-to-text showing the code for students to learn code.
  \end{itemize}
\end{frame}
